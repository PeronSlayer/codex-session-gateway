# Development

**Status: Implemented** — the development toolchain, six smoke tests, build and
quality checks are verified locally. Runtime integrations remain **Planned**.

## Prerequisites and commands

Use Git, Node.js 24.20.0 LTS and pnpm 10.34.5 as an unprivileged user. Node is
pinned in `.node-version`; pnpm is pinned in `package.json#packageManager`. Node
engines allow the 24.x major, and pnpm rejects incompatible engines or
package-manager versions. Follow [toolchain installation](toolchain.md) when
provisioning a host. Do not run Node, npm, pnpm or Git using sudo for
development.

```sh
pnpm install --frozen-lockfile
pnpm lint
pnpm format:check
pnpm typecheck
pnpm test
pnpm build
pnpm check:docs
pnpm check:secrets
pnpm audit --audit-level high
```

`pnpm format` applies formatting before the check. ESLint uses flat
configuration. Typecheck includes source, tests and Vitest configuration; build
uses a root TypeScript solution with project references and emits source
modules/declarations only. There are no inter-package imports yet, so no
speculative dependency graph is encoded. Add package dependencies and references
together when imports arise.

The six smoke tests import real component source modules and verify their names,
scaffold status and version. Compilation and direct imports of all six built ESM
modules have also been checked. These checks do not establish connector
compatibility or runtime security. `vitest.config.ts` uses projects instead of
the deprecated workspace file. The dashboard has no source, build script,
framework or test placeholder. Build output remains under ignored component
`dist/` directories.

The documentation checker validates required documentation, explicit feature
status, local Markdown file links and local anchors. It does not request
external URLs. The preventive secret checker checks Git candidates and staged
content for forbidden paths and common credential patterns without printing
matched values. It is heuristic and requires a manual staged diff review.
Neither checker accesses home credential stores or follows repository symlinks.

## Lockfile and lifecycle scripts

`pnpm-lock.yaml` was generated by pnpm, with public registry integrity hashes
for the resolved dependencies. `pnpm install --frozen-lockfile` succeeds without
changing it. Use that command for normal checkouts and CI. Use `pnpm install`
only when intentionally changing dependencies, and review the resulting graph
and audit before committing the lockfile; never edit it manually.

No resolved package requires `preinstall`, `install` or `postinstall` scripts.
`onlyBuiltDependencies: []` permits none, and `strictDepBuilds: true` makes
unreviewed dependency builds fail installation. The earlier speculative esbuild
allowance was removed: the resolved Vite uses Rolldown and does not need it. If
a future update introduces a lifecycle script, inspect the exact package and
version before adding a narrow authorization. Do not bypass the check.

## GitHub independence

GitHub Actions is **configured but not externally verified**. The account
currently prevents jobs from starting because of a billing restriction. The
complete suite above runs locally without GitHub authentication, runners or paid
features. Workflow definitions use only `ubuntu-latest` and the same
`.node-version` and `packageManager` pins. No artifact upload or self-hosted
runner is configured. Successful local results do not imply successful hosted CI
or CodeQL analysis.

## Dependencies and versioning

Existing direct dependency versions were retained: their engines and peers are
compatible with the verified toolchain. TypeScript 5.9 is within
typescript-eslint's supported peer range. Zod is declared only in `protocol` for
the explicitly planned runtime contracts; there are no schemas yet. No
application framework, MCP SDK, transport client or database dependency is
included.

The registry reports ESLint 9.39.5 as deprecated. It passed local lint and
audit, so it was retained instead of performing an unrelated major-version
upgrade. Review its replacement under ROADMAP M0.4.

Use `pnpm changeset` for changes affecting future package consumers, and
reference a ROADMAP identifier in design changes. Changesets is configured to
version private packages without publishing or tagging them.
`pnpm version:packages` is for a reviewed future versioning change, not part of
normal verification. There is no release workflow or registry publication
authorization.
